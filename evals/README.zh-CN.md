# 评测

[English](README.md)。如果中英文内容不一致，以英文版为准。

这些评测用于衡量某个技能是否改变了真实智能体的实际行为。每个用例都在 Claude Code 中运行，分别在安装该技能和未安装该技能的条件下进行。基线条件省略被测技能；其他宿主能力可能仍然保留。

## 运行

```bash
evals/run.sh debug --runs 3 --concurrency 3
python3 evals/report.py /tmp/hl-evals debug:1 --failures
```

依赖：`uvx`、已完成认证的 `claude` CLI，以及 `PATH` 中的 `pytest`。成本因用例和模型而异。请使用有上限的批量运行。

| 变量 | 默认值 | 作用 |
|---|---|---|
| `EVAL_MODEL` | `sonnet` | 智能体使用的模型 |
| `EVAL_WORKSPACE` | `/tmp/hl-evals` | 运行输出目录 |
| `EVAL_SKILLS` | `skills/` | 技能根目录，例如用于衡量某项修改的旧版副本 |
| `EVAL_SKILL` | `hl-<suite>` | 要安装的技能，当它不是 `hl-<suite>` 时使用 |
| `EVAL_MAX_COST` | 未设置 | 可选的运行后成本阈值（美元）；它会停止之后的用例，但不是正在进行中的支出上限 |
| `EVAL_CLAUDE_SETTINGS` | 未设置 | 通过 `--settings` 传入的原生 Claude 设置文件，用于明确的权限与沙箱策略 |
| `EVAL_CHECK_SHELL` | 系统 shell | 接收 `-c <command>` 以执行命令检查的可执行文件；对于不可信的工作区，请使用经过操作系统沙箱隔离的 shell |

封装脚本会移除 harness 的跳过权限标志，并默认重试次数为零。原生的 Claude 权限仍然生效。请使用隔离的 `CLAUDE_CONFIG_DIR` 和明确的沙箱策略。在开始一批运行之前，先在一次全新的试运行中验证技能发现和命令权限。

Claude 的沙箱不覆盖评分后的命令。请将 `EVAL_CHECK_SHELL` 设置为一个经过沙箱隔离的 shell，它应移除私有环境变量，并阻止向外写入、读取私有数据以及访问网络。否则，命令检查会保留调用者的权限。转录归档发生在命令执行之前。

在安装了所有技能且不点名任何技能的条件下，测试自然触发：

```bash
EVAL_SKILL=hl-debug EVAL_WORKSPACE=/tmp/hl-evals-routing evals/run.sh routing --runs 3 --concurrency 3 --no-baseline
python3 evals/report.py /tmp/hl-evals-routing routing:1 --failures
```

## 目录结构

套件以其技能去掉 `hl-` 前缀后的名称命名：套件 `debug` 测试的是 `hl-debug`。

| 路径 | 内容 |
|---|---|
| `<suite>/evals.json` | [agent-skill-eval](https://pypi.org/project/agent-skill-eval/) 格式的用例 |
| `<suite>/files/<fixture>/` | 复制到智能体工作区中的文件 |
| `<suite>/files/<fixture>/.eval-setup.sh` | 可选：一个 shell 脚本，用于在工作区中构建用例所需的 git 状态（分支、提交、已暂存的变更），智能体启动前会被删除 |
| `<suite>/checks.json` | 每个用例的确定性检查和必需的语义审查标准 |
| `<suite>/repo.sh` | 可选：为这些用例构建一个 git 仓库，作为 `--source-repo` 传入 |
| `check.py` | 运行检查的评分后钩子 |
| `report.py` | 按技能、检查类型和配置统计通过数 |

每项检查属于以下三类之一：
- `task`：用户需要的结果，例如正确的缺陷行，或通过的测试。
- `contract`：技能的输出契约，例如首行或证据表。
- `trigger`：在 `routing` 中，智能体是否选择了正确的技能。

输出检查读取最终回答。过程检查读取会话转录及其子智能体转录。评分后钩子将它们归档到运行的 `outputs/` 之下，设置了 `CLAUDE_CONFIG_DIR` 时使用该目录。报告读取归档，但不改变归档。

正向命令检查要求已完成的工具结果；被拒绝、未完成和后台运行的尝试不构成执行证明。`ran_before_edit` 要求编辑请求之前有一个完成时间戳。负向的命令和技能检查会统计尝试次数，即使它们被拒绝。请求快照不计为额外的工具调用。

`not_exposed` 在最终回答、序列化的助手条目、工具结果和原生回执中搜索所给的模式，包括子智能体。用户提示词和 API 请求快照被排除。即使最终回答已作脱敏处理，只要工具结果中读取了夹具的原始密钥，该检查即失败。缺少转录时无法通过；失败证据从不复制匹配内容。此已知夹具检查不能证明经过编码、拆分、部分或未被捕获的泄露，也不能证明已保存产出的合规性。

已完成的 shell 请求可能包含非零退出码。它们不能证明每个匹配的子命令都已运行或通过；合格性审查必须检查实际输出和产出。

工具调用次数的最小值要求已完成的调用。最大值统计所有尝试，包括被拒绝的调用。

`report.py` 会使用当前的 `checks.json` 重新评估输出检查和过程检查；工作区检查和命令检查保留其记录的结果。命令检查会把最终回答作为标准输入接收。

`graded` 类型的检查要求对照源码推导出的判定标准，对完整的回答、报告和工具轨迹进行有记录的审查。缺少证据时，对应标准保持未评分。评分后钩子不会根据关键词推断语义结果。缺失或被跳过的评分使运行不完整，而不是通过。请保留审查者身份、证据、被评估的字节，以及 `evals.json` 和 `checks.json` 的 SHA-256 摘要；仅凭判定标准的标签无法确定其措辞。`report.py` 不验证这一来源记录。审查结论一致不是运行时证明。不要自动把夹具内容发送给评分者：原生 `agent-skill-eval` 0.7.0 的评分会读取工作区文件，可能暴露机密夹具，并且会忽略大于 4 KiB 的文件。

工作区比较使用基于文件描述符的 POSIX 相对打开方式，并拒绝被检查路径中的符号链接或非常规文件。单文件检查不会检查无关路径。

报告既接受 harness 的单次运行布局，也接受重复运行布局。它们会将计划中的运行与最近一次调用的 `summary.json`、`progress.jsonl` 和 `run_meta.json` 对齐。缺失、跳过、过期或未完成的运行会被明确报告。缺失必需证据和 CLI 错误不能产生通过的运行。缺少早期尝试证据的重试是不完整的；其报告的成本只是小计。被删除文件和命令超时的检查会记录为失败，同时不丢失其余的评分。

任务检查接受任何表述正确结果的措辞，例如将“valid, fix it”视为 agree。需要技能专用词汇或格式的检查属于契约检查。

`gh`、`jira` 和 `acli` 是会失败的桩程序；选定的代码托管平台凭据会被移除，`gh` 配置目录为空。这些措施减少意外访问，但不隔离文件系统或网络。调用者必须自行配置这种隔离。Claude 自动记忆处于关闭状态，因为工作区路径可能重复。`hl-open-pr` 和 `hl-ci-fix` 的用例覆盖 `--dry-run`、拒绝，以及 GitHub 不可达时的停止。

跨套件的 eval id 必须唯一：agent-skill-eval 只用 eval id 为每个智能体工作区命名，因此两个 id 相同的套件并行运行时会相互破坏。一个单元测试会强制执行这一点。

不要期望裸智能体符合技能的契约。任务检查用于显示该契约是否损害正确性。只有当所有必需检查都通过、证据完整且 CLI 运行成功时，一次运行才算通过某一类。`p` 是单侧 Fisher 精确检验，用于比较各组运行的通过数。不完整或被排除的运行会使其显示为 `n/a`。早期调用遗留的运行也会抑制显著性结论，而不是悄悄地从审计中消失。

### 提示词深度

`ambitious` 套件覆盖：一个有边界的缺陷修复、用法语给出且缺少转化证据的请求、主观的小说创作、一个已经很具体的解析器任务、缺失的任务、无法验证的成功标准、需要独立检查的方法，以及一个不得变成工具项目的限时分析。它还覆盖：一份必须借用方法而不是角色的事后复盘（`range`）、一个更大目标只应出现在 Next 中的崩溃修复（`higher-outcome`），以及一个需要提出延伸目标的保守目标（`stretch-target`）。

使用 `evals/run.sh ambitious --runs 3 --concurrency 3` 运行。任务检查读取围栏中的提示词以获取用户的约束；契约检查读取输出格式、Next 选项以及是否没有编辑。还要对照每个回答的 `expected_output` 进行审查：正则表达式无法确定某个方法或检查是否可靠。使用 Sonnet，每个用例 3 次运行：任务检查使用技能时 33/33 次通过，未使用时 3/33；契约检查使用技能时 33/33，未使用时 0/33。

新上下文的模型样本检验的是指令，而不是宿主的技能发现或自然路由。无论是样本还是强制调用，都不能证明智能体会选择 `hl-ambitious` 而不是相邻的技能。

进行比较评测时，在生成之前固定请求和标准。保持模型和输入相同，隐藏技能身份，并按两种呈现顺序审查每一对结果。顺序之间不一致时，记为无定论。优先看重保持的范围、可用的一手材料、具体的方法，以及能拒绝看似合理的错误的检查，而不是输出长度或签名措辞。在某个用例上调优后，使用新的保留请求；保留失败和平局。模型偏好不能证明普遍优越或领域正确性。

### 安全审计变体

`security-audit` 套件有 5 个原始用例和 15 个变体，覆盖退款、助手操作、成员移除、支付 webhook 和邀请。变体字母顺序已打乱。每个 `expected_output` 现在都给出由源码推导出的判定标准，包括防御措施和缺失的事实。有限定条件的追踪也算作检出；缺失的 schema、隔离设置或下游实现不得自动变成漏检。

#### 历史比较，冻结判定标准 v1

这次比较没有使用 harness。每次运行都把技能和夹具复制到一个没有 git 的新目录，然后使用 `--model sonnet --effort medium --tools Read,Glob,Grep --safe-mode --restricted --setting-sources '' --strict-mcp-config` 和空的 MCP 配置运行 `claude -p`。基线是 1.4.0 版本。只读工具要求在回答中给出完整报告。当时没有审查智能体可用。一个盲评评分者（`claude-opus-5-5`，无工具，JSON schema）把完整回答分为断言、有条件、驳回或缺失四类。逐字引用经过自动检查和人工审查。旧判定标准把断言视为易受攻击变体的正确答案，把驳回或缺失视为已防御变体的正确答案，把有条件的处理视为无定论变体的正确答案。这些规则混淆了检出和确定性。

运行身份：Claude Code 2.1.309，观察到的运行模型为 `claude-sonnet-5-5`，中等推理强度，随机运行顺序，种子为 `20261026`。额外参数为 `--no-session-persistence --output-format stream-json --verbose --add-dir <skill>`。基线与 `8b221accb1b37ac6d79c383e0fff760749bee024` 处的 `origin/main` 一致。开发阶段的试运行不计入这些数字。本地合格性审查的轨迹不随仓库发布。

| 原 v1 标签 | 每个技能的运行次数 | 基线 v1 一致数 | 修订版 v1 一致数 |
|---|---|---|---|
| 易受攻击 | 8 | 8 | 5（3 次有条件） |
| 已防御 | 8 | 8 | 8 |
| 无定论 | 8 | 6（2 次断言） | 8 |
| 保留的 `invites` 系列 | 6 | 6 | 6 |

- 每个技能 24 次运行，基线花费 1.91 美元，修订版技能花费 3.75 美元；轮次中位数分别为 11 和 17。保留系列的运行分别花费 0.46 和 0.82 美元。
- 冻结的总数为 22/24 和 21/24。它们不是修正后的准确率估计：对源码的重新审查发现了合理的保留意见，以及另一个有源码支持的问题。没有确立整体提升。
- 在无定论的运行中，基线 8 次中有 7 次给未经证明的论断打了严重程度。修订版技能 8 次中 8 次都没有打分。
- 基线在全部 8 次易受攻击的运行中都返回了 `Exploitable`，没有独立检查。修订版技能返回 `Unreviewed exploit path`。
- 修订版的两次 `members-c` 运行让发现依赖于数据库级联删除；该夹具没有可以排除级联的 schema。一次 `webhooks-a` 运行要求进行部署检查。基线的两次 `members-a` 断言运行也指出了仓库内一个真实的缺口：移除事件在提交之后发布，且没有重试。
- 其他夹具局限包括 `refunds-b` 中未经验证的 PostgreSQL 隔离级别，以及较早系列中缺失的部署事实。这些分数反映的是声明的源码判定标准，而不是实际执行的漏洞利用。
- 修订版有六次运行在使用 `Unreviewed exploit path` 的同时指出了一个缺失的外部事实。随后收紧了该判定词的定义。`invites` 系列是在此之后编写的：2/2 次易受攻击的运行使用了该判定词，0/2 次无定论的运行使用了它。这早于判定标准 v2 和当前技能。
- 一个修订版回答把判定词放在了标题下，而不是 `Verdict:` 行中。
- 旧的正则表达式任务检查不能区分各变体。例如，`invites-b` 的发现检查匹配了解释防护措施的已防御回答。这些检查已被替换，但没有改写这些历史结果。
- 这些运行没有衡量 harness、自然路由、运行时复现，也没有衡量云、原生、客户端、本地平台、可用性和供应链指南。更早的一次报告编写冒烟测试通过了验证器；它不是关于当前字节的证据。

#### 修正后的源码判定标准和带版本的合格性审查

一位独立审查者在不阅读被评估回答的情况下，从源码推导出预期机制。修正后的判定标准区分源码追踪、决定性的防御措施，以及可能改变结论的缺失事实。它们接受有依据、等待审查的候选发现。它们不要求给出严重程度或确切的判定词才算检出。特别是：缺失的 schema 可能影响成员密钥的吊销；实际生效的隔离级别可能影响退款竞态；提交后的事件丢失与未知的消费者行为是两回事。

三个新的租户导出变体在指令设计时被预留：缺失租户绑定、由服务端推导的租户过滤，以及强制执行情况未知的外部存储。在 v2 中，它们的源码判定标准在生成回答之前冻结，每个用例和技能各运行两次。盲评评分者收到完整回答和判定标准，**但没有收到源码**；其评分细则在生成之后才完成。这些结果衡量的是与判定标准的一致性，而不是经过核查的引用准确性。

一次全新的 v3 在独立安全审查之后重复了这些用例。包含源码的评分细则、判定标准和哈希在十二次新运行之前冻结。评分者收到每个夹具文件和完整回答，但没有收到条件标签。这是一次回归重复，而不是一个新的未见系列。导出用例的回答和评分都没有被用来调整指令。两轮中所有支持性引用都与回答一致。

| 检查 | v2 基线 | v2 修订版 | v3 基线 | v3 已审查版 |
|---|---|---|---|---|
| 检出易受攻击的源码机制 | 2/2 | 2/2 | 2/2 | 2/2 |
| 解释了决定性的租户防御措施 | 2/2 | 2/2 | 2/2 | 2/2 |
| 指出缺失的下游强制执行 | 2/2 | 2/2 | 2/2 | 2/2 |
| 对已防御路径的误报 | 0/2 | 0/2 | 0/2 | 0/2 |
| 对所述论断给出无依据的确定性 | 0/6 | 0/6 | 0/6 | 0/6 |
| 实质性的源码引用错误 | 未检查 | 未检查 | 0/6 | 0/6 |
| 源码树未被改动 | 6/6 | 6/6 | 6/6 | 6/6 |
| 被拒绝的工具尝试 | 0 | 0 | 0 | 1 |

在这些结果上没有观察到改进。小规模合成样本存在天花板效应。候选状态没有被计为漏检。评分不是漏洞利用的复现。v3 修订版的一次运行尝试了一个超出范围的父目录 glob。它被拒绝；之后的读取和列目录都留在授权的夹具和技能目录内。这既不是权限合规的通过，也不是拒绝处理普遍可靠的证据。

v3 之后，一个示例预检被收紧，要求使用外部可信的 gitleaks 规则。没有其他技能字节发生变化。随后，一次全新的、允许写入的审计用最终字节生成了两份报告。只出现了 `Glob`、`Read` 和 `Write`。源码和技能副本保持不变。验证器以零退出；候选发现保持 `needs_validation`，没有审查者，且只有源码证据。这证明了报告的生成和一致性，而不是发现本身为真。

随后的审查在验证器中发现了二次复杂度的关系检查：一份包含 10,002 个范围条目、大小为 86 KB 的报告运行超过 3 秒。关系检查现在使用集合和祖先查找。一个回归测试把包含 20,000 条范围路径和 20,000 个追踪跳点的有效报告限制在 10 秒以内。在示例报告的 20,000 个变异副本上，新旧验证器返回了完全相同的错误列表。四份已存储的、由智能体编写的报告仍然通过验证。契约现在也写明了验证器早已强制执行的 1,024 字符路径限制；没有其他技能字节发生变化。没有任何智能体运行使用这些字节。

### 复杂 debug 用例和更深入的 debug 技能

第 62 轮为 `hl-debug` 增加了 4 个带干扰项的用例：

- `heisenbug`：一个 cron 计数为 0，而 `--verbose` 显示为 4。用户怀疑 cron 环境。原因是一个生成器被读取了两次。

随后，该技能借鉴了公开 debug 技能中的思路：
- 对可证伪的假设排序，并包含用户怀疑的对象；
- 在任意维度上二分（提交、输入、配置、依赖、环境、测试顺序），使用稳定的判定条件和 `git bisect run` 退出码；
- 污染源搜索；正常与故障的差异对比；在组件边界记录日志；
- 在被破坏的不变量上设置条件断点；
- “在同一处有两个假设失败：重读代码”；
- 在报告中写出预防措施和影响范围；
- 修复模式，仅在请求时启用：一个失败的回归测试、最小的修改、重新运行循环、删除调试日志，以及三次修复失败后停止。

由这些运行推动的修复：
- 那次真实审查把一个工具提示的显示称为“blocking”。严重程度现在取决于用户或调用方会遇到什么，需要先追踪调用方、防护条件、类型和 schema，并与基础分支比较。薄弱的测试属于有限问题。
- 旧技能的 `cr-revise` 在 3 次运行中有 2 次用英文回答，并保留了“bloquant”或“high”。专项参考文件使用的是 blocking/high/advisory 等级。现在所有文件都使用 `data or security failure`、`material bug`、`limited issue`、`cosmetic`。修订后的审查从不提及之前的严重程度。
- `--deep` 有一次在定时唤醒之后用一个迟到的回合替换了报告，还有一次在轮询后台子智能体的 shell 循环中挂起。子智能体现在在前台运行。
- 行号来自目标版本上带行号的读取，从不来自 diff 片段。

一次独立审查发现了 2 条危险规则和 7 个检查缺陷。缺少行号会让一个粘贴 diff 中的发现变为未解决，因此位置现在退回到文件和函数。一个未知的部署条件让发现变为未解决、判定为 `Clear`；审查者现在先阅读部署、配置和文档，并且 `Clear` 会统计未解决的候选，由第一个 Next 步骤来解决。检查修复，每项都有单元测试：法语 `Verdict :` 的空格、一个通过排除检查的裸 `generated/` 路径、通过 IDOR 检查的“authorization is unchanged”、匹配到“race”的“trace”，以及更多法语中的撤回和严重程度措辞。`cr-noise` 夹具移动了 protobuf 字段编号，这是第二个可能的缺陷；现在的重新生成只做新增。

这 6 项修复：回答语言跟随请求文本，而不是提交信息；子智能体返回后，第一行仍然是审查结论；注意事项点名基础分支；一个发现用带 `file:line` 的平实句子表述，不带标签；隐藏缺陷的测试修改从不单独成为一点；除非仓库显示存在混合版本部署，否则混合版本部署风险保持未解决。竞态检查现在接受法语“en même temps”和“simultané”。

简报必须告诉编写者逐字复制这些规则：有一次重新生成丢掉了语言规则，6 次运行用英文回答了法语请求。`--deep` 的命名检查现在接受列表（“The architecture, simplicity and security reviews found”）。

成本：在最后一次完整运行中，69 次困难运行花费 8.39 美元，15 次旧运行花费 2.59 美元。局限：每个用例 3 次运行，一个模型（sonnet），正则表达式检查，以及该工具提示被评为有限问题，因为它的文档字符串说明它显示的是未缩放的行。

对检查的三次独立审查发现了误通过、误失败，以及要求技能格式的任务检查。每个修复都有单元测试。`report.py` 使用当前检查重新运行输出检查和只读取回答的判定命令；其他命令保留记录的结果，检查被移到另一类时也一样。读取报告文件的检查也会读取回答，因此在聊天中给出的正确回答也能通过。复合检查已被拆分，因此删掉一个功能不会让另一个功能的检查通过。没有目标的用例带有一项“Invents no”检查，针对编造的计划、判定或轮次。`run.sh` 将 git 与全局 git 配置和钩子隔离。新的无目标检查在第 52 轮与基线一起运行：`hl-verify` text-none、`hl-challenge` lens-no-target 和 `hl-grill` no-idea 在两种配置下都是 3 次中 3 次通过。上面的 `hl-verify` 和 `hl-grill` 行早于这些检查。

由这些运行推动的修复，只使用技能重跑（第 51 到 54 轮），或与基线一起重跑（`hl-launch-marketing` 第 55 轮，`hl-startup` 第 53 轮，`hl-improve` 第 51 和 52 轮，`hl-security-audit` 第 52 轮）：
- `hl-security-audit` 快速模式保留了 MEDIUM 发现。快速模式现在会去掉它们：3 次契约运行中 3 次通过。
- `hl-startup` 快速 scout 写了 438 到 531 个词，上限为 440 词，第一次修复后为 474 到 508 个词。按部分划分的预算替代了总字数，快速模式去掉了构建草图和风险列表：第 52 和 53 轮 6 次运行中 6 次为 282 到 328 个词。
- `hl-launch-marketing` 经济分析没有以数字开头。第一行现在以数字给出最致命的那个数；它的示例不再使用用例自己的数字：第 55 轮 3 次运行中 3 次通过。快速渠道把实验放在表格下方的块中；现在它们放在表格行中。发布计划给出了场所规则，例如没有标签的自我推广比例；规则中的数字现在标注为公开或估计：第 54 轮 3 次契约运行中 3 次通过。
- 检查修复，每项都有单元测试：首行检查允许在首行之前有一个 `# title` 行；`hl-discover` 的限定范围运行检查曾让一次只承诺阅读顺序的运行失败；`pricing-low` 的标签检查现在针对买方的替代成本，即回答从估计中推导出的唯一数字；`100%` 的完成目标不算论断。`oracle.py` 区分标签（估计、实测、公开）、来源和被保留的数字：数字标签契约需要一个标签或一个来源，而虚假论断检查接受标签或拒绝，从不单独接受发布者名称。`hl-code-review --deep` 必须至少启动 diff 所需的六个专项审查者。

局限：
- 正则表达式和 `oracle.py` 检查的是契约。它们显示输出的形状，而不是其质量。
- 三次重复只能检测出较大的差异。
- 对于 `hl-challenge`（包括困难用例）、`hl-checkpoint`、`hl-ci-fix`、`hl-receive-review`、`hl-show-me` 和 `hl-spec`，`hl-code-review` 和 `hl-improve` 的最初用例，所有 `hl-security-audit` 用例，以及新的 `hl-deslop`、`hl-launch-marketing`、`hl-receive-review`、`hl-startup` 和 `hl-tickets` 用例，任务检查无法区分技能和基线：裸智能体也能得到正确结果。它们的收益在于契约。
- `hl-improve` 在新用例上的任务差距来自使用技能命令语法的提示词，例如“Run improve branch.”。裸智能体无法知道它们的含义，因此该差距高估了技能在结果上的收益。
- `oracle.py` 会把任何括号中的大写名称列表，例如“(ProZ, Reddit)”，当作具名来源。一份场所列表会被当作引用而通过。
- `hl-ci-fix` 和 `hl-open-pr` 没有针对真实拉取请求进行测试：没有用例读取真实的检查日志、推送或创建拉取请求。
- `pr-ready-stale` 和 `cr-rereview` 没有记录在案的 harness 运行。`cr-rereview` 的设置基于 code-review 仓库，尚未在 harness 中运行。它的分支本地历史不能证明之前的阅读覆盖范围；预期的审查现在覆盖完整范围。本地回归测试和评分 CLI 样本覆盖了增值税、按比例计费、机器人批准和恢复方面已知的误通过，而不是一般的语义正确性。被引用的发现仍可能通过，任何接近“split”的问题都可能满足方法检查，而不运行检查可能会因一次无害的“pytest”搜索而失败。
- `cr-idor` 的所有权检查拒绝了被测试的所有者审查请求，但不是所有的非发现。否定的授权论断和更宽泛的所有者签核措辞仍可能通过。
- 一个强制在直接“fix it”之前先提问的 `hl-improve` 用例已被删除：请求与用例相互矛盾。
- agent-skill-eval 会在每个工作区中运行 `git init`；不需要仓库的用例会在 `.eval-setup.sh` 中删除 `.git`。
- 裸智能体有时会写出工单，随后它的 CLI 不退出；这些运行会超时并被排除，因此 `hl-tickets` 的基线运行较少。
- 以 `--` 开头的提示词会让裸 `claude` CLI 失败；提示词请以一个单词开头。
