# Verification lenses

Choose from the actual boundary and its callers. These are ways to derive tests, not a claim that every project has every weakness. Use synthetic resources; do not expand authorization or build new infrastructure. Inspect the installed API's contract before choosing a repair.

- **Identity and ownership.** Hold the resource constant while changing the permitted actor; then hold the actor constant while changing resource or tenant. Check shared helpers, exports, background consumers, field-level updates and privilege changes. Confirm both legitimate owners still succeed. Replacing an object ID with a harder-to-guess ID is not authorization.
- **Interpretation and injection.** Follow data into its actual interpreter: query, command, template, document, regular expression or parser. Prefer parameter binding or context-specific safe APIs. Test an ordinary special character as data and an alternate attacker-controlled route to the same sink. A blacklist that blocks the reported string does not establish separation of code and data.
- **Paths, URLs and protocol changes.** Trace normalization, decoding, links, redirects and alternate transports through the final operation. Test a neighboring path that shares a string prefix, an equivalent representation and a permitted nested resource when applicable. A resolved-path check does not prevent a symlink swap before open; concurrent writable paths need an atomic or descriptor-based boundary, or remain unverified. Mock external destinations, not the guard under test.
- **State and concurrency.** Identify replay, expiry, revocation, retries, ownership transfer and check/use gaps. Derive a controlled schedule with the existing test framework when relevant. Preserve idempotency and legitimate retry behavior. Lack of a deterministic reproduction does not establish absence of a race.
- **Agents and delegated authority.** Trace untrusted context to deterministic tool dispatch and handler authorization. Test changed arguments, stale approval, cross-owner retrieval and an alternate tool entry point. A better warning prompt is not a repair for an overprivileged handler. Use inert instructions and synthetic outputs; never collect real secrets to prove disclosure.
- **Dependencies and release.** Verify the resolved artifact, affected feature and caller against the publisher's advisory, not copied notices alone. Distinguish mitigated versions, distribution backports and reachability. Check that a proposed upgrade preserves behavior and that build or update paths cannot replace reviewed inputs. Do not execute untrusted install hooks or fetch packages without permission.
- **Memory, parsers and resources.** Select relevant existing sanitizers, bounded fuzzers or malformed-input tests. Separate a crash, leak, exhaustion and unauthorized effect. Keep legitimate boundary-size inputs and cleanup paths covered. Do not perform unbounded stress tests or claim code execution from a crash alone.
- **Cryptography and disclosure.** Check standard API usage, authenticated context binding, randomness, expiry and error/output behavior with synthetic keys or markers supplied for testing. Do not invent cryptographic constructions, inspect real key material or hide sensitive output only after capture. Missing protocol or deployment facts stay explicit.

For each chosen check, record the public input, expected safe behavior, original observation, patched observation and legitimate control. Mark a lens inapplicable only with a source-backed reason. A broad checklist with no reachable input or decisive observation adds no assurance.
